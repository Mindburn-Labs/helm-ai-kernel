# HELM AI Kernel Claims

- Repo name: `helm-ai-kernel`
- Canonical role: Public HELM AI Kernel implementation: fail-closed execution kernel, CLI/API (including operator TUI), SDK/contracts, receipts, replay/conformance surfaces, and local headless onboarding proof path.
- Public/private: Public OSS repo.
- HELM normative status: Canonical HELM AI Kernel under UCS v1.3.
- Current status: Active implementation with Go server, guardian evaluation, receipt storage/verification paths, API contracts, Dockerfile, Helm chart, tests, and docs. Current public GitHub release: `v0.11.3`, which matches source `VERSION`. A `v0.10.5` and a `v0.11.2` tag exist without a GitHub Release; `CHANGELOG.md` records what each one published.
- Implemented capabilities: Guardian decision evaluation, API/server wiring, receipt persistence and verification primitives, external host evidence ingestion/verification/correlation, deployment assets, conformance/test scaffolding, Boundary Enforcement Profile compiler and posture attestor (HELM compiles systemd/nftables/cgroup enforcement artifacts from hash-bound policy input and attests the live posture; systemd/nftables enforce; drift fails closed at service start and on-demand attest runs, not continuously), signed offline update-bundle format and verifier (format + verifier only; no build tooling, no OTA mechanism), operator TUI with typed APPROVE/DENY ceremony, catalog `--format text|json` contract, receipts canonical inspect verbs, setup client lifecycle projection.
- Not implemented: No Console source code in this repo; no hosted Enterprise automation production claim; no named buyer production rollout claim; no L4 conformance claim; no eBPF, seccomp, TPM, hardware enclave, or packet-blocking enforcement claim unless a tested code path proves it; Kernel is not an `OrganizationRuntime`.
- Public claims: HELM AI Kernel is the fail-closed execution firewall for AI agents; dangerous actions must be denied or escalated before dispatch; receipts can be verified and tampering must fail; HELM can consume and correlate external host/network evidence without claiming host-level enforcement; local `mcp approve` does not mint MCP approval authority.
- Claim evidence: `core/cmd/helm-ai-kernel`, `core/internal/cli/tui`, `core/pkg/guardian`, `core/pkg/receipt`, `core/pkg/evidence/externalhost`, `core/pkg/correlation/hostaction`, `core/pkg/verifier/externalreceipt`, `core/pkg/boundary/profile`, `protocols/json-schemas/boundary`, `reference_packs/boundary-profile-v1`, `reference_packs/update-bundle-v1`, `deploy/appliance`, `docs/deployment/boundary-enforcement-profile.md`, `api/openapi`, `Dockerfile`, `charts/helm-ai-kernel`, `README.md`.
- Tests that prove each claim: `go test ./...`, API contract checks, demo receipt smoke tests after API routes are enabled, `make verify-boundary-profile-vectors`, `make verify-update-bundle-vectors` (Go + independent Python parity incl. fail-closed negative vectors), `core/cmd/helm-ai-kernel` TUI/format/receipts/setup lifecycle tests.
- Docs that mention each claim: `README.md`, `docs/`, `examples/`, deployment/runbook docs.
- Conformance boundary: `helm-ai-kernel conform` has no level shortcuts. `--level L1|L2` (also via `test conformance`) was retired in HELM-756 with gates G1-G15 and GX, because they could not return a truthful result; it exits 2. What runs today: `conform --profile SMB` runs gate G0 (build identity) only, exits 1 when it fails, and with `--signed` writes the report, its digest and a `.sig` file that holds an Ed25519 signature only when `HELM_SIGNING_KEY_HEX` holds a 64-byte private key, otherwise an explicitly unsigned digest (no release workflow sets that key, so `make conformance-release-report` produces the digest form); `conform --vector <file>` checks one external failure vector against its required assertions; `conform managed-agents claude-self-hosted` checks redacted live evidence for a self-hosted Claude managed-agents worker. `conform vectors` and `conform negative` list the negative execution-boundary vectors (expected verdict, reason code, receipt and no-dispatch assertions) without executing them; `go test -v ./pkg/conformance/negative` (in `core`) executes only the vectors that have a bound harness against a live Guardian and reports the rest as unbound. `L1`, `L2` and `L3` remain test-level labels inside `core/pkg/conformance`, with no CLI or API proof path. No `L4` or higher level is a public claim.
- Stale claims removed: Any unsupported hosted Enterprise automation, entitlement-enforcement, or production-conformance claim must remain absent until smoke-tested. Do not claim click-to-approve, YOLO mode, or Kernel-as-OrganizationRuntime.

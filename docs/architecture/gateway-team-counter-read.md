# Gateway team counter read

The gateway exposes `POST /v1/authority/team-counter:read` on its main listener. It reads one canonical TEAM admission limit from PostgreSQL. The caller presents a gateway-audience bearer token with the single scope `helm.gateway.read`; the token's tenant and workspace are the only identity source. The caller must be the applied plan's provisioner or the named team principal, registered as an active service principal. The worker and executor listeners do not serve this route.

The request is JSON with one `binding` object. Its [schema](../../protocols/json-schemas/gateway/team_counter_request.v1.schema.json) requires the exact `org_ref`, `version_ref`, `plan_digest`, `revision`, `team_node`, `mandate_id`, `limit_id`, `limit_version`, `unit`, `measure`, `window`, and `span`. Get the plan fields and node/limit fields from `GetProvisioning` on the same gateway. `revision` and `limit_version` are decimal strings, following proto JSON's int64 representation. The route rejects unknown fields, including caller-supplied tenant or workspace fields. It never selects a limit by unit alone.

The response [schema](../../protocols/json-schemas/gateway/team_counter_response.v1.schema.json) returns that binding, `cap`, `used`, `reserved`, `within_cap`, and each active `bucket` with its UTC start and exact `used` and `reserved`. All amounts are decimal int64 strings. For an hour, day, or month window, the read sums exactly the current `span` buckets; a windowless limit has the epoch bucket. It reads only the chosen limit ID. Parent, child, historical, and copied counters are not added. `within_cap` is `used + reserved <= cap`; a false value is observable rather than clamped away.

The read uses one PostgreSQL read-only `REPEATABLE READ` transaction under forced tenant RLS. `observed_at` is the database clock in the first data-read statement after tenant binding, and `db_snapshot` is PostgreSQL's `pg_current_snapshot()` from that statement. Subsequent reads use that same snapshot. The timestamp is an observation time, not the timestamp at which PostgreSQL created the snapshot; neither field is a signed receipt. The route writes no counter, hold, attempt, posting, or reservation. A current bucket without a materialized row returns `412 counter_not_materialized`; it never reports a fabricated zero.

The gateway verifies that the plan is current, its applying attempt belongs to the token workspace, the reader is the applied provisioner or team, the team node and holder match, the team service principal and mandate are active, the mandate is in its validity interval, the limit has the exact requested version and dimensions, and durable provision membership places that limit on this team in the same workspace. A missing organization in this scope returns `404 not_found`. A stale or mismatched binding returns `412 stale_binding`. An unrelated, inactive, or unregistered reader returns `403 permission_denied`. Missing or invalid authentication returns `401` or `403`. Bad JSON or binding fields return `400`; database failures return `503`. Every response is `Cache-Control: no-store`.

For a one second load sample, retain the exact binding and each response with its HTTP status, `observed_at`, and `db_snapshot`. A non-200 response invalidates that sample; do not coerce it to zero. Evaluate `used + reserved <= cap` for every successful sample. A plan or limit replacement makes the old binding stale and requires a separate run. This surface is the admission counter, not the model spending report from `GetProvisionBudget` and not a sum of per-attempt exposures. End-of-run hold and confirmed-usage reconciliation needs its own source-owned attempt/exposure evidence; this read alone does not establish that equality or a live T102 pass.
